# Benchmarking Methodology & Statistical Standards

**Platform:** Q-SHIELD Benchmark Laboratory (`bench.py`, `pages/5_Benchmark_Lab.py`)  
**Scope:** Real wall-clock timing and serialized byte dimensions across classical and post-quantum cryptographic primitives  

---

## 1. Principles of Empirical Cryptographic Benchmarking

All measurements generated by Q-SHIELD are collected live from actual Python and C-extension function calls on the user's host machine. **No timing values or serialized dimensions are fabricated, simulated, or hardcoded.**

### 1.1 High-Resolution Timing
Timings are measured using `time.perf_counter_ns()`, which accesses the highest available resolution hardware clock on the operating system (typically the CPU Time Stamp Counter / TSC), converted to milliseconds ($10^{-6}$ seconds).

### 1.2 Warm-up Passes
Every timed callable undergoes 3 unrecorded warm-up iterations prior to measurement collection. This eliminates:
- Page-fault latency and initial binary loading into process memory.
- CPU frequency scaling latency (transitioning from idle states to full clock frequencies).
- Python bytecode interpreter cache cold-starts.

### 1.3 Interleaved Pipeline Execution
When comparing complete encrypt/decrypt pipelines across Classical, PQC, and Hybrid modes, functions are executed in a **randomized round-robin interleaved order** each iteration:
```python
order = ["classical", "pqc", "hybrid"]
for _ in range(iterations):
    random.shuffle(order)
    for mode in order:
        measure(pipeline[mode])
```
This guarantees that no algorithm receives an unfair advantage from CPU L1/L2 data cache retention, memory allocator locality, or thermal throttling.

## 2. Statistical Metrics Reported

For every operation, Q-SHIELD records a full sample array of size $n$ (configurable between 10 and 200 iterations) and computes:

1. **Median ($50^{\text{th}}$ percentile):** The primary metric reported, robust against background OS interrupts and thread preemption.
2. **Mean (Arithmetic average):** Calculated via `statistics.fmean()`.
3. **Minimum:** The fastest observed execution time, representing the near-optimal CPU cache state.
4. **Maximum:** The slowest observed execution time, highlighting maximum latency outliers.
5. **95th Percentile ($p95$):** Reflects tail latency critical for SLA-sensitive network services.
6. **Standard Deviation:** Calculated via `statistics.stdev()`, measuring repeatability.

## 3. Scope of Measured Primitives

### 3.1 Key Generation
- **X25519 (Classical ECDH):** Scalar multiplication on Curve25519 via OpenSSL.
- **Ed25519 (Classical EdDSA):** Keypair generation on Edwards25519 via OpenSSL.
- **ML-KEM-768 (PQC KEM):** Module-LWE matrix generation and polynomial sampling.
- **ML-DSA-65 (PQC Signature):** Module-SIS matrix generation and rejection sampling.
- **Hybrid (X25519 + ML-KEM-768):** Joint keypair generation.

### 3.2 Key Establishment
- **X25519 Key Exchange:** Raw ECDH scalar multiplication (`sk.exchange(pk)`).
- **ML-KEM-768 Encapsulation:** Generating shared secret $\text{ss}_k$ and ciphertext $c$.
- **ML-KEM-768 Decapsulation:** Re-deriving shared secret $\text{ss}_k$ from $c$ using secret key.
- **Full Key Establishment:** Complete sender and receiver workflows incorporating HKDF-SHA256 and public parameter context binding.

### 3.3 Digital Signatures
- **Ed25519:** Signing and verifying a 1 KiB payload.
- **ML-DSA-65:** Signing and verifying a 1 KiB payload.

### 3.4 Symmetric Encryption
- **AES-256-GCM:** Direct 1 KiB AEAD encryption and decryption under a 256-bit key with a 96-bit nonce and associated data.

## 4. Hardware Context Capture

To ensure reproducibility, each benchmark run captures and displays:
- **Operating System:** Platform release and architecture (e.g. `Windows-11-10.0...-SP0`).
- **Python Version:** Complete interpreter build (e.g. `Python 3.13.15`).
- **CPU Information:** Host processor identifier and available logical core count.
- **Library Versions:** `cryptography` and `pqcrypto` versions.
- **Timestamp:** Exact ISO 8601 execution time.

## 5. Interpreting Results & Engineering Trade-Offs

Empirical results reveal the core trade-offs of the post-quantum transition:

1. **Computational Speed vs. Bandwidth:**
   - ML-KEM-768 encapsulation and decapsulation execute very quickly in C (often faster or comparable to elliptic curve scalar multiplication).
   - However, ML-KEM-768 public keys ($1,184$ bytes) and ciphertexts ($1,088$ bytes) are roughly $35\times$ larger than X25519 ($32$ bytes).
2. **Signature Overhead:**
   - ML-DSA-65 signatures are $3,309$ bytes, compared to $64$ bytes for Ed25519. In bandwidth-constrained IoT or high-frequency certificate handshakes, this increase requires architectural consideration.
3. **Hybrid Prudence:**
   - The hybrid mode incurs the combined computational time and key sizes of both X25519 and ML-KEM-768, representing an intentional trade-off: paying a small overhead in exchange for total security against both algorithmic flaws in newly standardized PQC and future quantum computers.
